# معماری بازسازی پنل سازنده حساب صراف

## مرز پروژه و حفاظت از داده

- مخزن مرجع مطالعه: `roohalla41-blip/-1`، شاخه `release/restore-build`؛ فقط‌خواندنی.
- محیط پیاده‌سازی: مخزن مستقل `roohalla41-blip/B2`، شاخه `rebuild/creator-panel-core-2026-11-11`.
- مقصد Supabase در شاخه B2 از `public/runtime-config.js` خوانده می‌شود و پروژه مستقل B2 است؛ این شاخه نباید به URL یا کلید پروژه A1 تغییر داده شود.
- هیچ اتصال، migration، SQL، یا عملیات داده‌ای روی Supabase اصلی A1 انجام نمی‌شود.
- این شاخه به‌صورت مستقل build می‌شود و نباید از workflow انتشار production استفاده کند.

## اصول معماری

1. **Server-authoritative RBAC:** نقش، وضعیت حساب، دسترسی کمک‌سازنده و مجوز هر عملیات در Postgres/RPC سمت سرور تعیین می‌شود. مقادیر React، localStorage و مخفی‌کردن تب‌ها فقط برای رابط کاربری هستند و مرجع امنیت نیستند.
2. **Fail closed:** اگر RPC تأیید نشست یا مجوز اجرا نشود، پنل دسترسی نمی‌دهد؛ هیچ فهرست دسترسی کش‌شده‌ای در مرورگر جایگزین سرور نمی‌شود.
3. **حداقل دسترسی:** سازنده اصلی همه ۲۶ ماژول را مدیریت می‌کند؛ کمک‌سازنده فقط ماژول‌های واگذارشده را می‌بیند و به‌صورت پیش‌فرض فقط مجوز مشاهده دارد؛ کاربر عادی هیچ دسترسی مدیریتی ندارد.
4. **ثبت ممیزی:** عملیات تغییردهنده باید در مسیر سروری مجاز اجرا و با شناسه عامل، ماژول، عملیات، هدف، نتیجه و زمان ثبت شود. گذرواژه، توکن و داده حساس نباید در لاگ نوشته شوند.
5. **بدون حذف سخت:** برای دسترسی‌ها و کنترل‌های مدیریتی از تعلیق/غیرفعال‌سازی استفاده می‌شود؛ حذف فیزیکی حساب یا سوابق مالی در این هسته وجود ندارد.
6. **تفکیک داده:** کد پنل جدید در B2 مستقل است. هیچ سرویس یا متغیر محیطی A1 در آن قرار نمی‌گیرد.
7. **قابلیت مشاهده وضعیت:** هر ماژول باید وضعیت اتصال، سطح آمادگی و خطای واقعی را نشان دهد. ماژول پیکربندی‌نشده نباید با داده ساختگی سبز نمایش داده شود.

## لایه‌ها

- **React UI:** داشبورد مرکزی، منوی ۲۶ ماژول، جست‌وجوی ماژول، نمایش وضعیت و فرم‌های مدیریتی.
- **Client API:** `src/lib/creatorAdminApi.js`؛ تنها واسط UI به RPCهای مدیریتی جدید.
- **Authentication:** نشست HMAC موجود B2؛ هر درخواست RPC با هدر `x-app-token` ارسال می‌شود.
- **Authorization:** توابع `creator_admin_*` در migration اختصاصی B2؛ نقش فعلی از جدول `users` خوانده می‌شود و ادعای نقش داخل مرورگر به‌تنهایی پذیرفته نیست.
- **Persistence:** جداول موجود B2 به‌همراه جداول جدید `creator_module_settings` و `creator_admin_audit_logs`. migration فقط در B2 است و تا زمان بازبینی/اجرا، قابلیت‌های وابسته با وضعیت «نیازمند راه‌اندازی» نمایش داده می‌شوند.

## مدل دسترسی

| هویت | حدود دسترسی |
|---|---|
| سازنده اصلی (`users.role = creator`) | دسترسی کامل به ۲۶ ماژول و تنظیمات مرکزی |
| کمک‌سازنده | فقط کلیدهای موجود در `builder_access.allowed_tabs`؛ مشاهده به‌صورت پیش‌فرض؛ عملیات تغییردهنده فقط با مجوز صریح در `allowed_actions` |
| کاربر عادی، صراف، کارمند، مشتری و مدیر صرافی | بدون دسترسی به پنل سازنده، مگر آنکه سازنده اصلی به‌صورت کمک‌سازنده دسترسی مجزا واگذار کند |

نکته: نقش `admin` در RBAC قدیمی B2 به معنی مدیر صرافی است و در این معماری به‌طور خودکار معادل سازنده اصلی نیست.

## مسیر اجرا

1. موجودی و نگاشت ۲۶ ماژول ثبت شده است.
2. قرارداد RBAC و migration سروری B2 آماده شده است؛ هنوز روی Supabase اجرا نشده.
3. گام بعدی: build، بررسی خطاها و سپس انتقال ماژول‌ها به API سروری یک‌به‌یک.
4. هیچ کدام از عملیات مدیریتی تا وقتی endpoint و مجوز سمت سرور آن پیاده و آزمایش نشده باشد، «عملیاتی» اعلام نمی‌شود.
